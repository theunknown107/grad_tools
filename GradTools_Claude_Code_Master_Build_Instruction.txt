=================================================

Document type:
Master implementation instruction for Claude Code

Project:
GradTools

Primary objective:
Build a student-focused academic utility platform that initially targets VTU and VTU-affiliated colleges, beginning as an experimental website and later becoming an Alpha release suitable for demonstration to the user's college and, eventually, VTU.

IMPORTANT:
This file is the controlling instruction for the Claude Code development workflow. Claude Code must follow it thoroughly. Do not silently skip phases, invent requirements, or move from documentation into implementation without the required approval.

================================================================
0. PROJECT CONTEXT
================================================================

GradTools is based on the Project Ideas Playbook concepts W8, W12, W13 and M1, expanded into one integrated academic utility platform.

Relevant source concepts:
- W8 — VTU Results & Notification Watcher
- W12 — Syllabus-to-Question-Bank Mapper
- W13 — SEE Prediction Engine
- M1 — Bunk, CGPA & Marks-Needed Companion

GradTools combines those concepts with:
- results and result notifications
- exam and academic announcements
- result/status caching
- SGPA and CGPA calculations
- backlog tracking
- marks statistics
- academic calculators
- recommendations/suggestions
- previous-year question papers
- model question papers
- syllabus browsing
- question-frequency analysis
- academic/timetable management
- attendance tracking
- bunk/attendance planning
- student profile
- later: deeper academic intelligence and institutional integrations

Product thesis:
"Students currently have to switch between multiple disconnected sources and tools to accomplish routine academic tasks. GradTools brings useful academic functions together in one simple, functional student application."

Do not position GradTools as a replacement for VTU.

Intended institutional positioning:
"GradTools is a student-facing utility layer that makes existing academic information easier to access, understand, organize and use."

Development strategy:
A. Build GradTools as an experimental website.
B. Use it personally and with a small group of students.
C. Stabilize it and release an Alpha version.
D. Use the working Alpha as the demonstration product for the user's college.
E. Only after product evidence and institutional interest exist, explore a formal relationship/integration with VTU.

The product must therefore be designed for eventual institutional credibility from the beginning, without pretending that it already has institutional endorsement.

7. DATA QUALITY PRINCIPLES
================================================================

Treat correctness as a first-class product feature.

External academic data lifecycle:
RAW -> PARSED -> NORMALIZED -> VALIDATED -> PUBLISHED

Never skip validation.

Prefer explicit freshness indicators such as:
"Last updated: ..."

If source data is uncertain:
- mark it
- avoid overconfident UI
- retain provenance
- prevent silent overwrite where possible

For results:
correctness > speed

It is acceptable to say:
"GradTools detected a change in the configured public result source."

Do not say:
"Your official result is released"
unless that has actually been established.

================================================================
8. SCRAPING RULES
================================================================

Scraping is a subsystem, not the core architecture.

All external sources must be accessed through replaceable adapters.

Conceptual interface:
ExternalSource -> fetch -> parse -> normalize -> validate -> publish

Every scraper must have:
- timeout
- retry policy
- backoff
- rate limit
- cache
- fixture tests
- failure state
- provenance
- change detection

Never:
- bypass CAPTCHA
- collect or proxy student credentials
- aggressively hammer a source
- evade technical restrictions
- describe unofficial access as official

If automated access is uncertain, STOP and ask the human before implementation.

================================================================
9. RATE LIMITING
================================================================

Do NOT use AI for rate limiting.

Rate limiting must be deterministic and enforced by application/infrastructure logic.

Potential dimensions:
- IP
- account
- endpoint
- source
- time window
- burst

During experimental scraping use conservative limits.

For result-day spikes, scale through:
- caching
- stale-while-revalidate where appropriate
- background ingestion
- CDN/cache
- deduplication

Never scale by sending more requests directly to VTU.

================================================================
13. AI PRINCIPLES
================================================================

AI is for language/semantic work, not truth-critical deterministic logic.

Good uses:
- question-to-syllabus mapping
- semantic duplicate detection
- question grouping
- natural-language academic explanations
- recommendation summaries

Bad uses:
- SGPA calculation
- CGPA calculation
- attendance calculation
- authorization
- rate limiting
- source authenticity
- database integrity

Where AI is used:
- record model/version
- ground against source data
- preserve evidence
- protect against prompt injection
- define fallback
- use confidence where meaningful
